## v1.4.1 Ownership and External-IO Boundary

A12-A20 add security/routing doctrine, not new host support. The runtime boundary is:

- Div1.HCO owns routing, staffing requests and circuit-breaker control records; raw issue text is untrusted input and must not directly instruct Div2, Div4, Div7 or runtime tools.
- Div3.Treasury owns budget, paid/credentialed access and secret-grant decisions; grant records must be scoped, reviewable and free of plaintext secrets.
- Div6.External is the only division that may contact external web, customer/vendor, external API/service, external document or external-agent surfaces.
- Div6 returns raw external evidence only to Div5.QualificationsLibraryLearning; internal consumers receive sanitized packets, rejections or needs-human outcomes from Div5.
- External IO requests, raw evidence bundles, sanitized knowledge packets, grants, staffing packets and HCO control packets are inert artifacts. Native issue/document/comment readback may carry them when available, but those artifact surfaces do not prove external API access, plugin actions, approvals, events, state durability, Hermes, GSD-Pi or UI support.

Operationally, the external-IO gate remains fixture-first unless a future runtime evidence file proves the exact automation path. A valid runtime promotion must cite `plugin-bos-light/capabilities.paperclip-runtime.json`, include Paperclip version/build, and show surface-specific create/readback, registration, invocation or render proof without reusing S04 native artifact proof for unrelated surfaces.

## Adapter Contract Rules

- `plugin-bos-light/src/runtimeCapabilities.ts` mirrors capability keys and status vocabulary only; `plugin-bos-light/capabilities.paperclip-runtime.json` remains the evidence source of truth.
- `InMemoryPaperclipAdapter` and `InMemoryBOSPersistence` are test/draft-only seams. They keep pure BOS Light logic executable without implying Paperclip host support.
- Requested manifest capabilities distinguish integration intent from confirmed runtime capabilities; manifest entries are not proof that the host can load, register, render, or invoke them.
- S04 native issue/document/comment readback proof is not plugin registration proof. S05 records the current plugin/UI ledger in `docs/14_PLUGIN_UI_SURFACE_PROBES.md`; no BPI, Blueprint, Betting Table, Eval Gate, or Circuit Breaker feature flow should depend on a plugin runtime surface until that exact surface has S05-style evidence.

## Persistence and State Boundaries

Native artifact-first persistence remains the durable policy. S04 confirms that this sandbox can create/read a native issue, issue document, and issue comment containing BOS artifact evidence, so those surfaces are preferred for visible artifact records when available. Plugin state remains cache/overlay only unless a runtime round-trip and restart/readback proof exists.

S03 Blueprint and S04/S05 fixture envelopes still expose `selected_surface`, `artifact_ref`, `fallback`, and cache-overlay diagnostics. Cache-overlay saves and loads remain `cache-overlay-only`; they are useful for UI speed and diagnostics, but they are not durable truth and must be reconstructable from native issue/document/comment artifacts or markdown-only fallbacks.

Native approvals are separate from native artifacts. Comment or markdown review requests may help humans, but they must never populate native approval ids/statuses. `approvals.native` remains `unvalidated` until live create/readback proof exists.

## Events, Polling, and Activity Fallback

`events.issue_lifecycle` is `unvalidated` and `events.terminal_runs` is `fallback-only`. Circuit Breaker and gate transitions must work through explicit tool/action invocation and bounded polling before they depend on event delivery. When events are missing, use active-run polling with jitter/backoff and activity-log or issue-comment fallback.

S04 records zero activity log writes. `activity.logging` remains `unvalidated`; document/comment artifacts are visible evidence, not activity-log proof.

## Approval and Request Ownership

Approval/request ownership stays with Paperclip-native approvals. `approvals.native` is `unvalidated`; `registration.actions` only requests an action seam and does not prove native approval creation. Fallbacks may create an issue/comment asking humans to review a batch, but must not substitute a local/test-double decision for Paperclip-native approvals.

S04 created zero native approvals. Betting Table rows may only become approval-requested when a separately validated native approval response returns id/status and live readback proof.
